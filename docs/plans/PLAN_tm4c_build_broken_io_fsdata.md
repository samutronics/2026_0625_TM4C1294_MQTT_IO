## Symptom
`buildProject mqtt_io` → `../io_fsdata.h:2:10: fatal error: 'lwip/apps/fs.h' file not found` (while compiling `io_fs.c`).

## Root cause (validated 2026-08-24)
- `mqtt_io/io_fsdata.h` is a **TM4C-only** generated file, but it was regenerated by the **CC35x1** tool. Its header reads `/* Generated by platform/cc35x1/tools/makefsdata.py - do not edit. */` and line 2 is `#include "lwip/apps/fs.h"`.
- `lwip/apps/fs.h` is CC35x1 **newer-lwIP** nomenclature. TivaWare ships **lwip-1.4.1**, whose `fs.h` lives at `.../lwip-1.4.1/apps/httpserver_raw/fs.h` (already on the TM4C include path). The TM4C file must include the bare `fs.h`, and its `struct fsdata_file` layout must match old lwIP.
- Regressed in commit `00395e0` ("cc35x1: … fix web-FS regeneration") — a CC35x1 change that ran the CC35x1 FS generator over the TM4C file and committed the cross-contaminated output. `git diff HEAD` is otherwise clean; this is independent of the BLE-demo removal (Plan 8), just surfaced by its build check.

## Steps
1. Find how the TM4C web-FS (`io_fsdata.h`) was **originally** generated (makefsfile per `build-tooling`); there is no `mqtt_io/tools` or `mqtt_io/*.bat` in the tree today.
2. Regenerate `mqtt_io/io_fsdata.h` with the correct TM4C generator so it emits `#include "fs.h"` and the old-lwIP `fsdata` layout. Do **not** just hand-edit line 2 — verify the whole file matches lwip-1.4.1's `fs.h` API.
3. Add a guard so the CC35x1 prebuild (`platform/cc35x1/tools/prebuild_fs.bat` / `makefsdata.py`) can **never** write `mqtt_io/io_fsdata.h`.
